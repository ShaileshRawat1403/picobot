# Pico UI principles

Pico should feel like a quiet thinking room: a local place to ask, examine,
make, and keep the useful trace of work. Its interface can be philosophical
without becoming vague, and calm without hiding state.

## Field-notes language

- Prefer warm paper, ink, muted teal, and one restrained warm accent.
- Use editorial typography for meaning and plain UI typography for controls.
- Let whitespace and short labels carry hierarchy; avoid dashboard decoration.
- Treat memory, context, missions, and artifacts as pages in a working journal.

## Conceptual, but legible

- Copy may invite reflection (“make room for the work”), but actions must stay
  concrete (“Confirm”, “Inspect”, “Review approval”).
- Evidence should be visible beside the work it explains, never hidden behind
  decorative metaphors.
- A calm empty state should tell the owner what is absent and what to do next.
- Hermes is a flow reference only. Pico keeps its own visual language and its
  narrower personal-workbench boundary.

## Product boundary in the UI

- Show capability and profile state before exposing execution affordances.
- Distinguish “supplied to this turn” from “available in the workspace”.
- Keep approvals, lifecycle transitions, and provenance explicit and local.
- Make inspectors reversible: every evidence panel has a clear close path and
  a direct link to the fuller evidence view when the owner wants more detail.
- Avoid notification density, gamification, and catalogue-style integration
  surfaces.
